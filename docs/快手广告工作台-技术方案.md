## 0. 结论摘要（TL;DR）

| 维度 | 结论 |
|---|---|
| 接入身份 | 必须以「开发者」身份申请磁力引擎开放平台账号（广告主 / 代理商 / 第三方服务商三种角色），线下签合同/邮件审批，再创建应用拿到 `app_id` + `secret`（一个开发者最多 3 个应用） |
| 鉴权模型 | OAuth 2.0 授权码模式。`auth_code`（10 分钟、一次性）→ `access_token`（1 天）→ `refresh_token`（30 天）。三段 scope：`report_service`（报表）、`ad_query`（账户查询）、`ad_manage`（创建/修改广告），**三者都需要才能支撑本项目** |
| 架构底线 | `secret` 绝不能进浏览器。**必须走后端 BFF 中转**，前端只对接自家后端，由后端统一管 token、限流、重试、落库 |
| 最大技术风险 | 不是接口数量，而是 **限流 + 权限白名单 + 异步一致性**。创编类 QPM 仅 200~600，且大量能力需运营加白；批量建计划必须做成「本地任务状态机 + 断点续跑」，不能做成同步批量接口调用 |
| 推荐技术栈 | React + TypeScript + Vite + Ant Design + ECharts（前端）；NestJS + Prisma + SQLite（后端）。**前后端同语言**，桌面化时后端几乎零改造 |
| 打包路径 | 主推 **Electron + 内嵌 Node 后端子进程**（复用全部 Web 代码，改造量最小）；备选 Tauri v2 + Node sidecar（体积小 10 倍，接入成本略高） |
| 交付节奏 | P0 授权+只读盯盘（最快见效）→ P1 批量创编 → P2 异常监控告警 → P3 打包 exe |

## 1. 需求拆解

### 1.1 两条主线

**主线 A：批量上计划（写入侧）**
- 一次操作在多个广告账户下批量创建 计划 / 广告组 / 创意（三层结构）
- 名称、预算、出价、定向、素材、落地页等参数模板化、变量化
- 创建结果可追溯、可回滚（批量暂停/删除）、可导出
- 失败要能定位原因并**单点重跑**，而不是整批重来

**主线 B：日常盯盘与异常监控（读取侧）**
- 多账户数据聚合看板（消耗、曝光、点击、转化、成本、ROI）
- 小时级 / 天级趋势，多维度下钻（账户 → 计划 → 组 → 创意/素材）
- 异常自动识别 + 告警推送 + 处置动作闭环

### 1.2 隐含需求（容易被漏掉但必须做）
- **多账户统一管理**：一个开发者下面往往挂几十到几百个广告账户，需要账户池 + 授权状态巡检
- **配置资产沉淀**：定向模板、素材库、落地页、转化工具 ID 都要在本地建索引，否则每次建计划都要实时查一遍接口，直接撞限流
- **操作审计**：谁在什么时候用哪个模板批量建了什么、花了多少预算 —— 这是投放团队的实际管理诉求
- **幂等与防重复投放**：误点两次不能建出两批计划，这是真金白银的损失

## 2. 开放平台能力与权限梳理

### 2.1 接入门槛与身份

| 项目 | 说明 | 对本项目的影响 |
|---|---|---|
| 开发者角色 | 广告主 / 代理商 / 第三方服务商 | 广告主角色只能操作**注册主体下**的账户；要操作别的公司主体需走邮件审批加主体 |
| 申请流程 | 需磁力引擎销售/代理商开通开发者权限 → 线下审批（服务商需签入驻合同，约 7 个工作日） | **这是最长周期项，必须第 1 天启动**，否则会阻塞整个项目 |
| 应用管理 | 添加应用时填「应用名称 + 应用图标 + 授权回调地址」，创建后系统生成 `app_id` / `secret` / 授权链接 | 一个开发者最多 3 个应用，建议按「生产 / 测试 / 备用」或「不同业务线」拆分 |
| 回调地址 | 用于接收 `auth_code`，限制 5 次/月修改 | 一次定好，别反复改 |
| 沙箱环境 | 平台提供沙箱测试环境 | 联调阶段优先用沙箱，避免误操作生产账户 |
| 主体绑定 | 跨主体授权需邮件申请（附授权函 + 双方营业执照） | 若涉及多主体客户，提前规划 |

### 2.2 授权与鉴权链路（关键路径）

```
① 浏览器打开授权链接
   https://ad.e.kuaishou.com/openapi/oauth
     ?app_id={app_id}
     &scope=["report_service","ad_query","ad_manage"]
     &redirect_uri={回调地址}
     &state={随机串}

② 用户选择授权方式
   ├─ 基于广告账户授权：指定一个或多个广告账户
   └─ 基于用户授权（罗盘）：该快手 ID 下全部广告账户

③ 授权成功 → 重定向到回调地址，并拼接 auth_code
   {redirect_uri}?auth_code=xxxx&state=xxxx

④ 后端用 auth_code 换 token
   POST /rest/openapi/oauth2/authorize/access_token
   Body: { app_id, secret, auth_code }
   Resp: { access_token, access_token_expires_in,
           refresh_token, refresh_token_expires_in }

⑤ 后续所有业务接口在 Header 带：Access-Token: {access_token}

⑥ 到期前刷新
   POST /rest/openapi/oauth2/authorize/refresh_token

⑦ 查询当前 token 下已授权的广告账户
   POST /rest/openapi/oauth2/authorize/approval/list
```

**有效期（务必写进代码，不要靠记忆）**

| 凭证 | 有效期 | 备注 |
|---|---|---|
| `auth_code` | 10 分钟 | **一次性**，用完即废，可重新走授权拿新的 |
| `access_token` | 1 天 | 每次重新授权会重置 |
| `refresh_token` | 30 天 | 用它换新的 access + refresh |

**scope 权限对应关系**

| scope | 覆盖能力 | 本项目是否必须 |
|---|---|---|
| `report_service` | 报表查询（账户/计划/组/创意/素材/人群） | ✅ 盯盘必需 |
| `ad_query` | 账户查询（账户信息、计划/组/创意的配置读取） | ✅ 配置同步必需 |
| `ad_manage` | 创建与修改广告（含素材上传、人群管理等） | ✅ 批量上计划必需 |

> ⚠️ 授权链接里的 scope 是**授权时一次性确定**的。如果一开始只勾了 `report_service`，后面要做批量创编就得**重新走一遍授权**。所以第一版就把三个 scope 全带上。

### 2.3 核心接口清单

以下按本项目的使用场景分组。路径均为 `https://ad.e.kuaishou.com` 下的 REST 路径，统一 POST + JSON。

| 接口 | 路径 | 用途 |
|---|---|---|
| 获取 token | `/rest/openapi/oauth2/authorize/access_token` | auth_code 换 token |
| 刷新 token | `/rest/openapi/oauth2/authorize/refresh_token` | 续期 |
| 授权账户列表 | `/rest/openapi/oauth2/authorize/approval/list` | 同步已授权账户池 |
| 广告主资质信息 | `/rest/openapi/v1/advertiser/info` | 取账户名称、一二级行业（行业决定可用优化目标） |

| 程序化创意 | `/rest/openapi/gw/dsp/advanced_creative/create` | `/rest/openapi/gw/dsp/advanced_creative/update` | `/rest/openapi/gw/dsp/advanced_creative/list` |

**批量状态操作（启停/删除）**

| 接口 | 路径 | 备注 |
|---|---|---|
| 计划状态 | `/rest/openapi/v1/campaign/update/status` | 支持传 `campaign_ids` 数组 → 批量 |
| 广告组状态 | `/rest/openapi/v1/ad_unit/update/status` | 支持传 `unit_ids` 数组 → 批量 |
| 创意状态 | `/rest/openapi/v1/creative/update/status` | 支持传 `creative_ids` 数组 → 批量 |

> 📌 **重要设计约束**：计划层和组层**没有**真正的批量创建接口，只能循环调用；只有创意层有 `batch_update`。所以「批量上计划」在本项目里 100% 是**本地任务编排**，不是调一个批量接口。
> 📌 创建时可通过 `put_status` 直接建为暂停态（1=投放中，2=暂停），**这是安全闸门**：批量建完先停着，人工确认后再一键放开。

**报表通用请求参数（很重要）**

| 参数 | 说明 |
|---|---|
| `start_date_min` / `end_date_min` | **增量拉取**，格式 `yyyy-MM-dd HH:mm`，可精确到分钟 —— 盯盘实时同步靠它 |
| `start_date` / `end_date` | 按天拉取，格式 `yyyy-MM-dd` |
| `temporal_granularity` | `DAILY` 天粒度 / `HOURLY` 小时粒度 |
| `report_dims` | `adScene`（广告场景）、`placementType`（站内/联盟） |
| `page` / `page_size` | 最大 2000 |
| `campaign_ids` / `unit_ids` | 单次查询 ID 数 **不超过 5000** |

**数据时效性（写进调度策略）**

| 数据类型 | 延迟 |
|---|---|
| 实时报表 | 分钟级（分钟内） |
| T-1 型数据 | 次日 **09:00** 更新完成 |
| 实时报表可查范围 | **近 7 日**（例：今天 25 日，最早可查 18 日） |

> 📌 这意味着：**盯盘看板 = 实时报表（近 7 天）+ 本地落库（历史）+ 异步报表（补历史/大范围）** 三者组合。不能只靠实时接口。

### 2.4 配额、限流与硬性上限

| 项目 | 数值 | 应对策略 |
|---|---|---|
| 默认 QPM 分级 | 一级 1000 / 二级 2000 / 三级 3000 / 四级 4000 / 五级 5000 | 新应用默认一级；可用量增长后可申请提级 |
| 账户维度 计划/组创编 QPM | **600** | 按账户维度限流 |
| 创意 / 程序化创意创编 QPM | **400** | 单独限流桶 |
| 批量接口 QPM | **200** | `batch_update` 类单独限流桶 |
| 自适应限流 | 超时率达 20% 触发限流，**1 分钟后恢复** | 必须监控超时率，主动降速 |
| 分钟级总量 | 1000 次/min（分钟限制触发后暂停调用，3 分钟自动恢复） | 全局令牌桶兜底 |
| 单账户计划总数 | 最多 **500** 个计划（另一处文档口径为「创建上限 1000 个」） | 创编前做容量校验 |
| 单日创建上限 | 计划 1000/日；广告组 600/日；创意+程序化+批量 合计 2000/日 | 批量任务分批 + 跨日排队 |
| 异步报表 | 20 次/日 | 精打细算，只在必要时用 |
| 应用上传 | 200/日 | 素材上传排队 |
| 单次查询 ID 数 | ≤ 5000 | 自动分片 |

**报错处理原则**
- 按返回 `code` 区分三类：**可重试**（限流/系统繁忙/超时）→ 指数退避重试；**参数错**（字段非法/区间越界）→ 标记失败并给出修正建议，不重试；**权限错**（无权限/未加白）→ 直接告知需加白，不重试
- 附录有完整「报错 code 枚举值」，建议离线抓取后落成本地字典表，前端直接给中文提示

### 2.5 权限白名单（加白项）—— 项目排期必须提前确认

以下能力**必须联系运营/产运同学加白**才能使用，不是代码问题：

- **资源位**：双列信息流（`scene_id=7`）、内容消费资源位（56）、激励视频（24）、开屏（27）、联盟优选（1 / 10）
- **定向**：地域 IP（`ip_type`）、智能人群包、智能定向 Pro、行为意向 4.0、运营商定向、商圈定向（`district_ids`）
- **出价**：CPC（`bid_type=2`）在搜索广告场景
- **营销目标 / 结构**：周期稳投（`periodic_delivery_type=1`）、程序化创意 2.0、原生投放（`outer_loop_native`）、搜索广告、快手号短剧推广
- **应用**：自定义落地页 URL、应用商店优先下载、快小游小游戏推广

> ✅ **行动项**：项目启动第一周，先用「白名单查询」接口 + 运营沟通，把账户白名单现状列成一张表，反过来约束创编模板的能力范围。

### 2.6 其他必须记住的平台规则
- **物料退场**：一年以前已暂停/删除的计划、组、创意会被冷存，**只能点对点查询，不能编辑**，跨级查询也不支持。本地库要标记这类物料状态，避免任务反复失败。
- **DPA 级联**：DPA 动态商品广告创建单元时会级联创建 `photoId=0` 的空壳创意，单元与创意 1:1，任务编排要特殊处理。
- **年龄定向字段升级**：老字段 `age` / `ages_range` 已下线，必须用 `ages_range_v2` 或 `age_v2`。
- **价格单位统一为「厘」**：1 元 = 1000 厘。前端必须做元/厘转换并做好校验提示，这是最容易出错的地方。

## 3. 网页端技术方案

### 3.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | React 18 + TypeScript + Vite | 生态最全，组件库/图表库选择多；TS 保证接口字段类型安全 |
| UI 组件 | Ant Design 5 | 表格、表单、弹窗能力极强，大量数据密集型界面首选 |
| 图表 | ECharts 5 | 支持大数据量、多维度下钻、双轴，国内运营看板事实标准 |
| 数据请求 | TanStack Query | 缓存、重试、轮询开箱即用，盯盘场景天然契合 |
| 状态管理 | Zustand | 轻量，不引入 Redux 的样板负担 |
| 表格虚拟滚动 | antd Table virtual / react-window | 万级计划列表不卡 |
| 后端框架 | **NestJS（Node.js + TypeScript）** | 模块化 + DI，天然适配「按业务模块拆分」；**与前端同语言**，DTO 类型可共享，桌面化零改造 |
| ORM | Prisma | 迁移管理清晰，SQLite ↔ PostgreSQL 切换成本低 |
| 数据库 | SQLite（默认）→ PostgreSQL（可选） | 桌面版零依赖；团队部署版可切 PG |
| 队列 / 调度 | 自研轻量队列（SQLite 持久化）+ NestJS Schedule；服务端版可换 BullMQ + Redis | 桌面版不能强依赖 Redis |
| 日志 | pino | 结构化日志，桌面端可落文件 |
| 部署（服务端） | Docker Compose（app + pg + redis 可选） | 一套配置两用 |

**为什么后端选 NestJS 而不是 Python/FastAPI？**
虽然 FastAPI 写 API 很快，但本项目的硬需求是「**同一套代码要能同时跑在服务器和 exe 里**」。NestJS 编译出来就是一个 Node 进程，Electron 里可以直接 `fork`，前端构建产物直接塞进渲染进程 —— 不改一行代码。Python 方案要多一层 PyInstaller 打包 + Electron sidecar 通信，链路更长、坑更多。

### 3.2 架构原则（三条不可妥协）

1. **密钥不过河**：`app_id` / `secret` / `access_token` 只存在于后端。前端拿到的永远是自家后端的业务 token。
2. **一切外部调用走队列**：任何对快手开放平台的调用都经过统一网关（限流 + 重试 + 审计 + 缓存），禁止业务代码直连。
3. **本地优先、状态自持**：本地库是唯一事实源（Source of Truth），外部接口只是数据来源。所有创建的任务先落库再执行，保证可恢复、可审计。

### 3.3 五个核心机制设计

#### 机制 1：多账户 Token 生命周期管理
- 每个广告账户（或罗盘用户）对应一条 `oauth_account` 记录，存 `access_token` / `refresh_token` / 过期时间
- **提前 30 分钟自动刷新**（不要等到过期），刷新失败进入「需重新授权」状态并在前端高亮
- `refresh_token` 30 天到期前 7 天开始告警
- 所有业务调用前经 `TokenProvider.get(advertiserId)`，内部判断是否需刷新
- 授权回调地址落地为一个后端路由，自动完成 `auth_code → token` 兑换并落库

#### 机制 2：限流与并发控制（决定批量任务能不能跑起来）
- **三层令牌桶**：
  - L1 全局桶：1000 QPM（保护整个应用）
  - L2 接口类型桶：创编 600 / 创意 400 / 批量 200 QPM
  - L3 账户维度桶：同账户创编串行化
- **自适应降速**：统计滑动窗口超时率，> 15% 主动降速，> 20% 暂停 1 分钟（对齐平台自适应限流阈值）
- **ID 分片**：单次查询 ID 超 5000 自动拆批
- **失败退避**：1s → 2s → 4s → 8s，最多 4 次，超限转「待人工处理」

#### 机制 3：批量创编引擎（本项目最核心的模块）
把「批量上计划」建模成 **任务 → 任务项 → 分阶段步骤** 三级状态机：

```
BatchTask（批次）
  └─ BatchItem（一行 = 一个广告组，或一份"计划+组+创意"组合）
       ├─ Step 1: create campaign   → 存 campaign_id
       ├─ Step 2: create unit       → 存 unit_id
       └─ Step 3: create creative   → 存 creative_id
```

关键设计点：
- **幂等键**：`advertiser_id + 计划名 + 组名 + 批次指纹`。同批次重跑不会重复创建
- **前置预校验**（把失败挡在调用之前，能减少 60%+ 的失败）：
  - 优化目标 `ocpx_action_type` 是否与账户营销目标、行业匹配
  - 预算/出价是否在合法区间（元→厘换算 + 上下限）
  - 素材是否已审核通过、是否超绑定上限
  - 落地页/应用/人群包是否属于该账户
  - 账户计划数是否已达上限
  - 所需能力是否在账户白名单内
- **断点续跑**：任务可暂停/恢复，从第一个未成功步骤继续
- **安全闸门**：统一以 `put_status=2`（暂停态）创建，人工核验后一键批量启用
- **结果回写**：每条记录的成功/失败/原因/外部 ID 全落库，支持导出 Excel 和「仅重跑失败项」

#### 机制 4：数据同步引擎
三路并行，互为补充：

| 通道 | 频率 | 范围 | 用途 |
|---|---|---|---|
| 增量实时 | 每 5~15 分钟 | 近 7 日（用 `start_date_min`/`end_date_min`） | 盯盘实时数字 |
| 日级对账 | 每日 09:30 | 昨日全天 | 修正 T-1 数据、日结报表 |
| 异步报表 | 按需（≤20 次/日） | 7 日以上历史 | 补历史、大范围导出 |

- 报表宽表设计：`fact_ad_stat_hour`（小时粒度）+ `fact_ad_stat_day`（天粒度），维度含 `advertiser_id / campaign_id / unit_id / creative_id / photo_id`
- 增量水位线（watermark）记录每账户每报表的已拉取时间点，避免重复拉全量
- 报表结果缓存 + 前端轮询错峰

#### 机制 5：异常监控规则引擎
规则 = **条件组合 + 生效范围 + 静默期 + 动作**：

| 规则类型 | 示例 |
|---|---|
| 阈值类 | 单计划小时消耗 > 500 元 |
| 成本类 | 转化成本 > 目标出价 × 1.3 且消耗 > 100 元 |
| 比率类 | 点击率 < 0.8% 且曝光 > 10000 |
| 突变类 | 消耗环比上一小时 ±50% |
| 状态类 | 审核拒绝、余额不足、学习期超 48 小时未过、连续 2 小时零消耗 |
| 结构类 | 计划下所有组已暂停但计划仍开启 |

- 规则用**可视化配置**（不用写代码），支持试运行预览命中结果
- **静默期 / 去重**：同一对象同一规则 N 小时内只告警一次，避免刷屏
- 告警通道：站内消息 → 企业微信/钉钉/飞书机器人 Webhook → 邮件（按严重级分流）
- 告警消息带**一键处置**入口（暂停计划 / 降价 / 跳转详情）

| 模块 | 职责 | 关键依赖 | 优先级 |

| M5 数据同步中心 | 三通道拉数、宽表落库、水位线管理、异步报表任务 | M1 | P0 |
| M6 盯盘看板 | 多账户总览、多维下钻、趋势、TOP 榜、自定义列 | M5 | P0 |
| M7 异常监控与告警 | 规则配置、巡检调度、去重静默、多通道推送、处置动作 | M5、M1 | P2 |
| M8 审计与运维 | 操作日志、任务日志、错误字典、系统设置、数据备份 | 全部 | P2 |
| M9 桌面壳（后置） | Electron 主进程、服务启动、开机自启、更新 | 全部 | P3 |

### 各模块实现要点

**M1 账户与授权中心**
- 首次启动向导：填 `app_id` / `secret` / 回调地址 → 生成授权链接 → 引导用户完成授权
- 授权方式支持两种：按账户授权、按罗盘用户授权（一次覆盖该快手 ID 下全部账户）
- 账户健康度面板：token 状态、最近同步时间、白名单能力、余额
- ⚠️ 回调地址需要后端可被公网访问（域名 + HTTPS）。桌面版要考虑提供一个中转方案或让用户填自己的域名。

**M2 素材与资产中心**
- 素材上传走队列（200/日上限），上传后轮询视频解码/审核状态
- 本地维护 `资产ID ↔ 名称` 映射，创编时直接选，不再实时查接口
- 定期（每日一次）增量刷新资产列表

**M3 创编模板中心**
- 模板 = 一套完整的「计划/组/创意」参数 + 变量占位符
- 命名规则支持表达式，如 `${账户简称}-${素材系列}-${定向}-${日期}`
- 模板版本化：改动留版本，历史批次可复现
- **定向强制走定向模板接口**（`template_id`），不要每次传完整 `target` 对象 —— 对象极大且容易踩校验

**M4 批量任务引擎**
- 支持的输入：Excel 导入（提供标准模板下载）、界面表单批量编排、复制历史批次
- 支持的输出：创建结果明细表、失败原因汇总、可重导的失败项清单
- 任务控制：暂停 / 恢复 / 取消 / 仅重跑失败项
- 进度推送用 SSE，前端实时显示「已完成 x / 共 y，失败 z」

**M5 数据同步中心**
- 调度分层：分钟级（近 7 日增量）、日级（T-1 对账）、按需（异步报表）
- 水位线 + 幂等写入（按 `advertiser_id + stat_date + stat_hour + 维度ID` 做 UPSERT）
- 数据量大时按账户分片、错峰执行，避免整点集中撞限流
- 数据保留策略：小时级保留 30 天，天级长期保留

**M6 盯盘看板**
- 三层视图：全局总览（多账户汇总）→ 单账户 → 单计划/组下钻
- 核心指标：消耗、曝光、点击、点击率、行为数、转化数、转化成本、ROI、余额
- 支持自定义列、自定义时间范围、小时/天切换、同比环比
- 表格用虚拟滚动；图表用 ECharts 支持框选下钻
- **注意**：快手是「涨红跌绿」，但如果做成本类指标请注意语义（成本下降是好事，但仍用绿色表示数值下降）—— 建议成本类指标用中性色 + 箭头，不套用涨跌色

**M7 异常监控与告警**
- 规则可视化配置 + 试运行
- 巡检按账户并发，注意与创编任务共享 QPM，需要统一调度优先级（**盯盘优先级低于创编，避免挤占创编配额**）
- 告警收敛：同一规则同一对象 N 小时静默
- 处置动作需二次确认 + 审计

## 8. 打包为 exe 的实现路径

### 8.1 方案对比

| 方案 | 体积 | 改造量 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|---|
| **A. Electron + Node 后端子进程** | ~150–200 MB | **最小**（Web 代码 100% 复用） | 生态成熟、调试方便、更新机制完善、Node 后端零改造 | 体积大、内存占用高 | ⭐ **主推** |
| B. Tauri v2 + Node sidecar | ~15–30 MB | 中（需 Rust 工具链 + sidecar 通信） | 体积小、启动快、内存低 | 需要 Node 运行时随包分发，跨端调试链路更长 | 备选（对体积敏感时） |
| C. Node SEA/pkg 打成单文件 + 系统浏览器 | ~80 MB | 小 | 最轻量、无 GUI 框架 | 体验像「本地网站」，无原生窗口/托盘体验 | 快速验证版可用 |
| D. 纯瘦客户端（后端常年部署服务器） | 小 | 最小 | 桌面端只是壳 | 依赖服务器、有公网和安全成本 | 团队版可考虑 |

### 8.2 推荐方案（A）落地细节

**进程模型**

```
Electron Main Process（主进程）
  ├─ 启动时：检查/初始化 SQLite、跑 Prisma migrate
  ├─ child_process.fork(server/main.js)   ← NestJS 进程
  │     └─ 监听 127.0.0.1:{随机可用端口}
  ├─ BrowserWindow.loadURL(`http://127.0.0.1:${port}`) 或 loadFile(前端构建产物)
  ├─ 托盘图标 / 最小化到托盘 / 开机自启
  └─ 退出时优雅关闭子进程
```

**关键技术点**

| 问题 | 解决方案 |
|---|---|
| 端口冲突 | 启动时由主进程申请空闲端口，通过环境变量传给后端子进程 |
| 数据库位置 | 存到 `app.getPath('userData')` 下，**不要放安装目录**（Program Files 无写权限） |
| 数据库迁移 | 每次启动跑 `prisma migrate deploy`，失败则回滚并提示 |
| 敏感信息存储 | `secret` / `access_token` 用 **Windows DPAPI**（`safeStorage` API）或 `keytar` 加密后落库，绝不明文 |
| 后端与本机互通 | 统一走 `http://127.0.0.1:{port}`，CORS 只允许该来源 |
| 单实例 | `app.requestSingleInstanceLock()`，避免多开导致同账户并发创编撞限流 |
| 前端路由 | 用 HashRouter，避免 `file://` 下 BrowserRouter 白屏 |
| 中文路径 | 构建产物路径与日志路径全部验证含中文/空格场景 |
| 日志 | pino 输出到 `userData/logs`，主进程崩溃时写入 crash dump |
| 自动更新 | `electron-updater` + 私有更新服务器或 GitHub Release |
| 代码签名 | Windows 需代码签名证书，否则 SmartScreen 会拦截（企业内部分发可暂缓，但要提前说明） |
| 混合模式 | 桌面端也保留「切换到远程服务器」的配置项，一套代码两种用法 |

**构建链路**

```
pnpm build:web      → apps/web/dist            （前端静态产物）
pnpm build:server   → apps/server/dist         （NestJS 编译产物 + node_modules 精简）
pnpm build:desktop  → electron-builder
                        ├─ windows: nsis 安装程序（x64）
                        └─ windows: portable 免安装版
```

**改造量评估**：由于前后端同语言、后端无外部强依赖（SQLite 本地化、队列本地化），从 Web 到 exe 的**增量改造集中在 3 个文件**（主进程、启动器、路径工具）+ 构建配置，业务代码基本不动。这也是推荐 NestJS 而非 Python 的根本原因。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 开发者资质审批周期长 | 阻塞全部开发 | 第 1 天启动申请；并联做 UI 与本地数据模型 |
| 权限白名单未开 | 部分创编能力不可用 | 开工前用白名单接口盘点，模板能力范围按白名单动态裁剪 |
| 限流导致批量任务慢/失败 | 批量上计划体验差 | 三层令牌桶 + 自适应降速 + 离线排队 + 断点续跑；预计单账户建 100 个组需 10~15 分钟量级 |
| 报表仅近 7 日 | 历史数据缺失 | 本地落库 + 异步报表补历史；上线越早，历史积累越全 |
| 接口字段频繁变更 | 代码失效 | 订阅平台更新日志；MAPI 网关做字段容错（未知字段忽略不报错）；映射层集中管理字段 |
| 误操作造成真实损失 | 资金损失 | 默认暂停态创建 + 二次确认 + 审计 + 批量操作预演（dry-run） |
| 密钥泄露 | 严重安全事件 | 后端持有、加密存储、桌面端 DPAPI、日志脱敏 |
| 多开并发导致限流 | 任务失败率上升 | 单实例锁 + 全局调度 |

## 10. 待确认问题清单

请在开发启动前确认以下事项：

1. **开发者角色**：是广告主身份、代理商身份，还是第三方服务商身份？（决定能操作哪些主体、是否需要签服务商合同）
2. **账户规模**：需要纳管多少个广告账户？分属几个主体？是否需要罗盘用户授权？
3. **投放形态**：主要投什么营销目标（应用安装 / 销售线索 / 电商下单 / 直播 / 短剧 / 小程序）？—— 这决定创编模板的字段范围
4. **回调地址**：是否有可公网访问的域名 + HTTPS 证书？（桌面版尤其需要确认）
5. **白名单**：现有账户已开通哪些白名单能力？（双列信息流、激励视频、开屏、智能定向 Pro……）
6. **告警通道**：走企业微信机器人、钉钉、飞书，还是邮件？
7. **部署形态**：是否只做单机桌面版，还是需要多人协作的服务器版？（影响数据库与队列选型）
8. **沙箱环境**：是否已有沙箱账户可用于联调？
9. **批量规模**：单次批量上计划的典型规模是多少（10 个组 / 100 个组 / 1000 个组）？—— 直接决定任务引擎的并发设计
10. **历史数据**：是否需要在授权日前更早的历史数据？（平台对授权日之前的数据需要单独支持）

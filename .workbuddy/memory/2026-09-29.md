### ⚠️ 重大发现：原计划第 3 步（「重试失败项」复用）走不通，已修

**问题**：`task.service.ts` 建任务时把请求体 `JSON.stringify` 冻结进 `BatchTaskItem.payloadJson`，
执行时 `JSON.parse` 回放。而原 `retryFailed` **只把条目状态重置为 PENDING**，不重建 payload
→ 点「重试失败项（34）」会把**旧 mapper 的产物原样重发**，仍缺 `auto_build_name_rule`，
依旧 401000。用户「修了就能直接重试」的假设不成立。

**修复**：
- 抽出 `private expandRows(rows: PlanRow[]): PendingItem[]`（纯函数，`createTask` 与重试**共用一份**实现，
  避免出现「建任务一套、重建一套」的第二份定义 —— idemKey/seq 规则只有一处）。
  `PendingItem` 类型提到模块级，移除 createTask 内的同名局部类型。
- 新增 `private refreshFailedPayloads(taskId, rowsJson)`：从 `task.rowsJson`（提交时已定稿、含去重后名称）
  重新展开，**按 `seq` 一一对上**失败/跳过条目，重写 `payloadJson`（+`displayName`）。
- `retryFailed` 在 `updateMany` 重置状态**之前**调用它。
- **降级设计**（宁可报原来的错，也不能把任务卡死）：`rowsJson` 为 null / 非法 JSON / 空数组 → 告警并**保留旧 payload**；
  seq 未匹配上 → 告警并跳过该条目；payload 与旧值相同 → 不写库。
- 方法在编译后的 JS 里是普通方法（TS `private` 仅编译期），因此可以用内存假 Prisma 直接驱动做单测。

### ⚠️ 本轮最重要的结论：快手报表「曝光三兄弟」的口径（官方字段字典原文）

| 字段 | 官方定义 | 本工作台用途 |
|---|---|---|
| `show` | **封面曝光数** | ❌ 不是展示数，只用于算「封面点击率」 |
| `aclick` | **素材曝光数**（实测**恒等于 played_num**） | ✅ **展示数**，也是点击率/千展的分母 |
| `photo_click` | **封面点击数** | ❌ 不是点击数，仅存档 |
| `bclick` | **行为数**（快手把「点击」称为行为数） | ✅ **点击数** |
| `action_ratio` | **行为率** = bclick / aclick | 点击率就取这个口径 |
| `impression_1k_cost` | 平均千次**封面**曝光花费 = charge/show×1000 | ❌ 未采用（动辄上千元） |
| `click_1k_cost` | 平均千次**素材**曝光花费 = charge/aclick×1000 | ✅ 本看板的「千展」 |

**实测证据（账户 107574991 / 2026-09-29）**：charge=2058.78、show=891、aclick=160398、
bclick=1206、played_num=160398、activation=175。
- 账户报表与素材报表同账户同日**逐字段完全相同**（891 / 160398 / 1206 / 2058.781）→ 口径可信。
- 平台自算 `action_ratio=0.00751785959181638` ＝ 1206/160398 ✓ 精确吻合。
- 10 账户抽样：`bclick/show` 得到 **1.07 / 2.36 / 3.10 / 1.35**（>100%，不可能）；
  `bclick/aclick` 与平台 action_ratio 逐条吻合。

**推论（以后别再用 show 当展示数）**：凡是要「展示数 / 点击率 / 千展」的地方，分母一律取 `aclick`；
`show` 只配 `photo_click` 用（封面点击率）。

### 因此修正了盯盘看板（用户没点名，但 135% 点击率是硬伤）
`report.service.ts` 的 `normalizeRow` / `sumRows` / `overview.totals` / `hourlyTrend` 统一：
`show ← raw.aclick`、`actionRatio = bclick/aclick`、`impression1kCost = charge/aclick×1000`，

## 项目启动：快手广告批量上计划 & 日常盯盘工作台

**项目目标**：网页端先行，后续打包为 Windows exe。

- 交付物：`docs/快手广告工作台-技术方案.md`

**关键技术结论（后续开发直接沿用）**
- 接入身份：需申请「开发者」资格（广告主/代理商/服务商），创建应用获取 app_id + secret（最多 3 个应用）。这是最长周期项，须最先启动。
- 鉴权：OAuth2.0 授权码模式。auth_code 10 分钟一次性 → access_token 1 天 → refresh_token 30 天。
- scope 三段：report_service（报表）/ ad_query（账户查询）/ ad_manage（创建修改广告），三者全需要。
- 所有业务接口 Header 带 `Access-Token`。
- 计划层、组层**没有批量创建接口**，只有创意层有 batch_update → 批量上计划必须自研本地任务状态机。
- 报表可查范围仅**近 7 日**，实时报表延迟分钟级，T-1 数据次日 09:00 更新 → 必须本地落库 + 异步报表补历史。
- 限流：创编 QPM 600（计划/组）、400（创意）、200（批量）；全局 1000 QPM；超时率 20% 触发自适应限流，1 分钟恢复。
- 日创建上限：计划 1000/日、组 600/日、创意合计 2000/日；异步报表 20 次/日；单次查询 ID ≤ 5000。
- 单位统一为「厘」（1 元 = 1000 厘）。
- 年龄定向老字段 age/ages_range 已下线，须用 ages_range_v2 / age_v2。
- 大量能力需运营加白（双列信息流、激励视频、开屏、智能定向 Pro、周期稳投等）。
- 物料退场：一年前暂停/删除的物料只能点对点查询，不可编辑。

**技术选型（已定）**
- 前端：React 18 + TypeScript + Vite + Ant Design 5 + ECharts 5 + TanStack Query + Zustand
- 后端：NestJS + Prisma + SQLite（桌面）/ PostgreSQL（团队）
- 关键理由：前后端同语言，桌面化时后端零改造，Electron 里直接 fork NestJS 进程
- 打包路径：主推 Electron + Node 后端子进程；备选 Tauri v2 + sidecar

1. 密钥不过河（secret/token 只在后端）
2. 一切外部调用走统一 MapiGateway（限流+重试+审计）

**模块划分**：M1 账户与授权 → M2 资产中心 / M5 数据同步 → M3 模板中心 / M6 盯盘看板 / M7 异常监控 → M4 批量任务引擎 → M8 审计运维 → M9 桌面壳

## 授权模型重构：token 从「账户维度」提到「凭证维度」（同日傍晚）

**起因**：用户提出「为什么授权是在单个账户进行？在磁力罗盘授权不是能一次性授权该罗盘下所有账户或自选账户吗？」

**用户是对的，而且比想象中更对。** 核实结论（三个独立来源交叉验证：巨宣网络 / 神策分析文档 / 超级编导帮助中心）：

快手提供两种授权方式，**在快手授权页上选择，不由授权链接的 URL 参数决定**：
- **基于用户授权** → 生效范围 = 该快手 ID（磁力罗盘 / 代理商）下的**全部**广告账户
- **基于快手广告账户授权** → 生效范围 = **勾选的一个或多个**广告账户（可多选/全选）

即：**授权链接是通用的**，覆盖几个账户取决于登录账号 + 页面勾选。原先"单账户观感"的根因不在链接，而在数据模型和引导缺失。

**重构前的三个真实缺陷**
1. **token 被复制到每个账户行** —— 罗盘授权 N 个账户就写 N 份完全相同的密文；刷新靠 `authBatchId` 批次去重兜底。这是把「一对多」硬塞进「一对一」。
2. **`approval/list` 调用方式错误** —— 官方文档（documentId=3025&menuId=3800）要求 `app_id`/`secret`/`access_token`/`page_no`/`page_size` **全部放 JSON body**；原实现把 `access_token` 放在请求头、漏传 `secret`、没有分页。
3. **界面没说清怎么选授权方式** —— 用户自然就登了单个广告主账号。

**重构内容**
- 新增 `AuthGrant` 模型：承载 token / 有效期 / 授权方式 / 授权主体 / 覆盖账户数；`OauthAccount` 去掉 token 字段改挂 `grantId`（`AuthGrant(1) ──< OauthAccount(N)`，级联删除）
- `TokenService` 全面改为凭证维度：`getGrantAccessToken` / `refreshGrant` / `syncGrantAccounts`；删掉 `PENDING_ADVERTISER_ID` 占位账户和 `authBatchId` 去重方案
- 授权链接通过 `state` 携带声明的授权方式（`<随机>.<USER|ACCOUNT>`），回调时校正入库标签
- 新增每日 07:10 罗盘账户自动对齐任务（新增自动纳管、已解绑自动停用）
- 前端账户页改为**按凭证分组**（Collapse），凭证级 + 账户级两级操作；接入设置页加授权方式选择与分步指引
- 授权类调用（access_token / refresh_token / approval_list）补上审计留痕

**实测踩到的新坑（重要）**
1. **`approval/list` 的响应外壳是 `{result, message, data}`，不是主网关的 `{code, message, data}`！**
   实测返回 `{"result":400,"message":"access token错误",...}`。已加 `readStatus()` 同时读 `code` 与 `result`。
2. **`approval/list` 传参方式已用真实请求验证**：全部参数放 body → 通过参数校验进入鉴权（返回「access token错误」）；
   `access_token` 放请求头 → 直接被拒（「查询分页参数必传」）。**必须放 body。**
3. 错误码 `402012 应用已下线或者不存在` 实测得到，已入 `ERROR_CODE_MAP` 归为 `PERMISSION`。
4. antd 这个版本的 `Collapse` 不支持 `loading` 属性，要用 `Spin` 包。

**验证结果**
- 后端 34 个产物零类型错误；前端 `tsc --noEmit` 零错误 + `vite build` 通过
- `state` 编码验证：`?authType=USER` → `.USER` 结尾；非法值回落 `.ACCOUNT`
- 健康检查已返回凭证/账户两层结构
- 审计留痕验证：`requestJson` 中 `auth_code` 为 `***`
- 数据库已重置重建（本地无正式数据，直接 `migrate dev` 重建迁移）

## 重要更正：授权链接**不是通用的**，域名由「授权入口」决定（同日深夜）

**起因**：用户反馈「生成的授权链接自动跳转到磁力智投了，而不是磁力罗盘」。

**上一节（授权模型重构）的结论有一处是错的。** 当时写下「授权链接是通用的」，
事实是：**快手有三个授权入口，域名不同**，链接用错域名就会跳到错误的平台。
上一轮只改了数据模型和界面引导，**没改链接域名**，所以问题根本没解决 —— 用户一打开就发现了。

**官方/第三方来源五处独立印证：**

| 入口 | 域名 | 附加参数 |
|---|---|---|
| 磁力罗盘（批量） | `https://developers.e.kuaishou.com/tools/authorize` | — |
| 磁力智投（单主体） | `https://ad.e.kuaishou.com/openapi/oauth` | `oauth_type=advertiser` |
| 代理商 | `https://ad.e.kuaishou.com/openapi/oauth` | `oauth_type=agent` |

- 罗盘流程原文：「浏览器中输入快手信息流广告**账户罗盘授权 URL** →
  登陆注册**罗盘**的快手 ID → 选择授权方式：基于快手广告账户授权 / 基于用户授权」
- `oauth_type` 取值：`advertiser`（广告主/服务商）/ `agent`（代理商）/ `ad_social`（聚星）

**这就是「为什么授权是单个账户」的真正根因**：链接落在磁力智投登录页，
用户只能按单账户授权，罗盘的「基于用户授权」批量能力压根没机会出现。

**改动内容**
- `packages/shared`：新增 `KUAI_OAUTH_URL_LUOPAN` / `KUAI_OAUTH_URL_AD`、
  `AUTH_ENTRY`（LUOPAN/ADVERTISER/AGENT）、`AUTH_ENTRY_META`（含 label/platform/url/oauthType/coverage/howTo）、
  `SCOPE_META`、`DEFAULT_SCOPES`；`KUAI_SCOPES` 补 `account_service`
- `AuthGrant` 新增 `authEntry` 字段（迁移 `20260924081825_auth_entry_model`）
- `buildAuthorizeUrl` 按 `authEntry` 选域名 + 拼 `oauth_type`；`AGENT` 入口强制 `authType=USER`
- `state` 升级为 `<随机>.<AUTH_ENTRY>.<AUTH_TYPE>`，`decodeState` 兼容旧两段格式
- 设置页：把「预期授权方式」单选改为**三入口选择**（标注跳转平台/域名/覆盖范围/分步指引），
  新增授权链接域名实时预览、scope 勾选、「仅复制链接」
- 账户页：凭证显示入口标签、可更正入口；单主体入口只纳管到 1 个账户时主动提示「是不是该走罗盘」

**实测结果（全部通过）**
```
LUOPAN     → developers.e.kuaishou.com/tools/authorize                          无 oauth_type
ADVERTISER → ad.e.kuaishou.com/openapi/oauth?oauth_type=advertiser
AGENT      → ad.e.kuaishou.com/openapi/oauth?oauth_type=agent  (authType 强制 USER)
不传/非法 authEntry → 安全回落 LUOPAN，不报错
state 解析：新格式三段正确；旧两段格式兼容；乱码返回 {}
```

**教训（写进长期记忆了）**
1. 「授权链接是通用的」这个结论**是错的**。授权入口（域名）和授权方式（范围）是**两个正交维度**。
2. 上一轮的错在于：只信了「授权方式在页面上选」这个正确的点，就顺推出了「链接通用」这个错误的点。
   涉及跳转/域名这类可外部观察的行为，**必须实际打开一次验证**，不能靠文档推理。
3. 数据库再次重置（结构变更），用户需**重新授权一次**。

## P1 收尾：创建后状态开关 + 官方文档逐字段核对
- 用户选择：状态**做成可选开关**（默认暂停），并同意**跑完整三层真实验证**。

### 决定性发现：只有广告组能在创建时指定状态
| 层级 | 创建时能否指定状态 | 做法 |
|---|---|---|
| 广告组 | ✅ `put_status`（**不传默认填充 1=投放中**） | 创建时下发 `put_status=2` |
| 计划 | ❌ 创建接口无状态字段 | 创建后补 `/v1/campaign/update/status` |
| 创意 | ❌ 创建接口无状态字段 | 创建后补 `/v1/creative/update/status` |

**关键推论**：组暂停 → 计划无投放中的组 → **不可能产生消耗**。
所以「暂停」这个保证由组层单独完成，计划/创意层的补调用失败**只降级为警告**
（写进 `lastError`，前缀 `[警告]`），绝不把已成功条目翻成失败。

### 真实创建抓出的三个 bug（均已修复）
1. **状态更新不能同时传单数主键 + 复数批量字段**：文档说「二选一或同时填均可」，
   但同值同时填报 `401000 存在重复的id`。改为只传复数形式后 code=0。
2. **`401000` 未进错误码表**：它是最常用的「业务校验不通过」码（出价越界、ID 重复都用它）。
   之前靠消息关键字兜底，而「建议出价**范围**在」不含「**取值范围**」这个连续词 → 漏判为 UNKNOWN，
   前端给不出可操作建议。已按官方「13.2 报错 code 枚举值」（documentId 2064）补全 30+ 条：
   限流 400001 / 权限 4000xx+4020xx / 参数 4010xx+4100xx / 凭证 4020xx。
3. **状态更新响应的 `errors` 字段没被检查**：响应是 `{campaign_ids, errors, campaign_id}`，
   只读成功列表会把「部分失败」瞒成「全部成功」——最危险的谎报。已显式检查并在任务上告警。

`app_id`/`package_id` 补 0；`image_token` 自动生成。

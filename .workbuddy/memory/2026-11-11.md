## 后端掉线根治（15:50，用户追问「我点了守护脚本怎么还没起来」）
- **查明两个真因**：
  1. `启动网页版.cmd` 里有一句 `netstat | findstr :7801` 检查——端口被占就直接 `echo [STOP]` 退出。用户双击时若旧服务还残留在 7801，脚本根本不进 launcher。
  2. `watchdog.cjs` 的单实例保护只看 `process.kill(pid,0)`——Windows 复用 PID 时会把旧 pid 文件误判成「已有守护在跑」，新进程打印一行就 exit 0，窗口一闪而过（用户看到的就是「点了没反应」）。
- **改造（核心：一个窗口 = 服务 + 守护）**：重写 `tools/web-launch.cjs`
  - 端口接管：启动时探测 7801，先写 lock 宣告接管，再 `taskkill /F /T` 清掉占用者（含上个会话残留），等端口释放后启动。
  - 常驻看门狗：子进程**任何原因**退出都重启（原版是「只有 .restart-intent 存在才重启，否则父进程一起退」，这就是掉线没人管的根因）；退避 1→2→4→…→60s，日上限 60 次。
  - 健康探测：60s 探一次 HTTP，连续 2 次无响应判定卡死 → 杀掉重启。
  - 让位机制：child 退出时读 lock，若 lock 已不是自己 → 说明新窗口接管了 → 静默退出（否则两个窗口互抢 7801 形成重启风暴）。
  - lock 按端口区分：`.runtime/launcher-<PORT>.pid`（否则测试实例会抢正式实例的锁）。
  - 日志 `.runtime/launcher.log`。
- **watchdog.cjs**：单实例判据改为「pid 存活 **且** 心跳文件 `.runtime/watchdog.beat` 3 分钟内更新」，每轮 tick 刷新心跳；`启动网页版.cmd` 去掉端口占用检查。
- **实测**：杀后端子进程 → 2s 恢复；7801 无主占用 → 接管成功；双实例 → 旧实例 20s 内让位退出，无互杀。两个 .cmd 保持纯 ASCII + CRLF。
- 遗留：会话里起的进程仍会被回收，**必须用户双击一次 `启动网页版.cmd` 完成交接**（新窗口接管后旧实例自动让位）。
